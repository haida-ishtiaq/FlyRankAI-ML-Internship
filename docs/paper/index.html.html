§0

Abstract

Content teams managing large page catalogs cannot manually review every page for staleness or decline, so they need a way to prioritize. This project asks: which pages should a content team review first, given limited reviewer time? A hand-written scoring rule (staleness × visibility × recoverable position) was built first, then compared against trained classifiers on the same client-grouped, leakage-checked split. Logistic Regression was the clear, validated winner — beating both the observed base rate and the rule baseline at every evaluated cutoff — while Random Forest underperformed the base rate at low K and was rejected despite its typical reputation as the stronger model. The result is a ranked, reason-coded action queue that gives a content team a defensible starting point for review, not a verdict on any single page.

§1

Introduction

Editorial and content operations teams often manage far more pages than they can realistically review in a given week or month. The decision this project supports is narrow and concrete: out of thousands of pages, which ones should a human reviewer open first? The people who act on this are content strategists or editors deciding whether to update, expand, fix metadata, or leave a page alone.

Why ranking, not a cutoff

The cost of getting this wrong is asymmetric. Flagging a healthy page wastes bounded reviewer time. Missing a genuinely declining page is worse — it's invisible, and the page keeps losing visibility unattended, compounding over time. This is why the system outputs a ranked list, not a hard yes/no cutoff: it lets a human apply judgment rather than treating the model as automatic.

§2

Data

This analysis uses the FlyRank ML Internship starter dataset: 30,000 pseudonymized content items across 32 clients, one row per content item, with client_id used only for grouping — never as a feature or in printed output. All metrics are trailing windows "as of" an implicit snapshot; there are no absolute calendar dates in this slice.

Two columns required deliberate exclusion to avoid leakage: impressions_last_30d and impressions_prev_30d, which can directly derive the decline label. Their exclusion was verified empirically — a model given these columns back showed an artificial jump in accuracy (ROC-AUC 0.671 → 0.825, a +0.15 jump), confirming they leak the outcome being predicted. A separate, stricter check reintroduced trend_pct — the value the label is computed from directly — and produced an even larger jump (0.578 → 0.999), confirming the leakage-detection process itself is sound.

Missingness in the data (scroll_rate, word_count) follows content_type rather than being random, so missing values were flagged with has_* indicator columns and imputed from training-set medians, rather than blindly filled with zero.

Scope limit

This is a 30,000-row convenience sample, not the full multi-million-row warehouse. Findings here are scoped to this slice and are not assumed to transfer to a larger release without re-validation.

§3

Methodology

Target

is_declining, defined as trend_direction == "down" — an observed 30-day-over-30-day trend computed upstream in the data, not a rule invented for this project. 54.2% of the starter dataset is currently declining by this definition.

Features

Ten page-level signals available before the decision moment — impressions_90d, ctr, avg_position, engagement_rate, scroll_rate, days_since_last_update, content_age_days, word_count, freshness_tier, days_with_impressions — plus missingness flags. avg_position == 0 was treated as "no position data," not rank zero (1,205 rows).

Baseline

A plain-language, non-fitted rule — a page is worth reviewing if it's stale (≥180 days since update), still visible (≥500 impressions in 90 days), and sits in a recoverable position band (10th–50th average position). This rule flagged only 14 of 30,000 pages for review, reflecting how restrictive a single-threshold rule is in practice.

Validation design

An 80/20 GroupShuffleSplit grouped by client_id, so no client's pages appear in both train and test. This split was frozen and reused identically across the baseline, both trained models, and all downstream audit and playbook work (see §2 for the leakage checks run against this feature set).

Success metric

Precision@K (K = 20, 50, 100), always reported alongside the base rate, since precision@K is meaningless without knowing what a random ordering would achieve.

Reading this table

These rule-baseline numbers differ from the baseline notebook's own stand-alone evaluation (0.70/0.48/0.42), which scored the rule against the full 30,000-row dataset. The rule itself is unchanged — evaluating it only against the harder, held-out client subset here is the fairer, apples-to-apples comparison against the trained models, and is the version treated as authoritative throughout this paper.

Logistic Regression beat both the base rate and the rule baseline at every evaluated K. Random Forest underperformed the base rate at K=20 and K=50, and lost to the simple rule at every K — a specific, documented negative result. Per the project's own standard (add complexity only when the comparison earns it), Random Forest was not shipped; Logistic Regression is the model the validation audit and action playbook build on.

Limitation — thresholded classification vs. ranking

These precision@K numbers describe Logistic Regression's strength at the top of its ranked list. At a default 0.5 probability threshold, its confusion matrix on the test split was TN=1,150, FP=1,864, FN=880, TP=2,269 — meaning a majority of its "declining" flags at that threshold are false positives. This doesn't contradict the precision@K results; it's a reminder that the model's real value is in ordering pages for review, not a blanket yes/no call at an arbitrary cutoff. The final playbook uses the ranked score directly, never a 0.5 cutoff.

Validation gap: random split vs. honest split

A random (non-grouped) split overstated performance relative to the honest, client-grouped split — mean precision@50 of 0.828 vs. 0.735 across 8 repeated splits, a measurable ~0.09 gap attributable to within-client memorization. This is exactly why the grouped split is the correct design for this question.

Error patterns

The model's mistakes cluster around three recognizable cases, drawn directly from its printed false-positive and false-negative samples:

  1. High-impression, recently updated pages still flagged. A page with 2,426 impressions and only 13 days since its last update was still flagged as declining — staleness alone doesn't guarantee decline.
  2. Very low-impression pages that are missed. Several false negatives had under 300 impressions with zero clicks — low visibility likely suppressed the model's confidence even though the page was genuinely trending down.
  3. Recently updated pages that decline anyway. The model reads "recent update" as reassuring, but has no way to know whether that update was actually effective.

Only Fix CTR — visible pages ranked in the top 20 whose click-through rate sits below the position band's median — shows a decline rate clearly elevated above the eligible-population base rate (0.665 vs. 0.596). Accuracy by traffic tier

Performance was uneven across visibility tiers, ranging from roughly 0.49 (top tier) to 0.59 (mid tier) accuracy — the model is measurably weakest exactly where a wrong call is most costly, and this is carried forward as a named limitation rather than averaged away.

§5

Limitations & honest framing

  • All findings here are observed and directional, not causal. The data shows association between signals and decline — it does not show that refreshing a page causes recovery. That would require a controlled experiment this dataset cannot support.
  • This is decision-support for a human reviewer, not an automated verdict. No claim is made that the model is "always right."
  • The dataset is a 30,000-row starter slice from 32 clients; results should not be assumed to transfer unchecked to a larger release or different data.
  • Precision@K varies meaningfully across different client-grouped splits (std. deviation roughly 0.06 at precision@50 across repeated splits) — a single reported number understates that variability.
  • Nothing in this analysis makes any claim about Google's ranking algorithm.
§6

Ranked recommendations

01

Prioritize the Logistic Regression–ranked queue over the hand-written rule for weekly review — it delivers meaningfully higher, validated precision (0.74 vs. 0.62 at K=50 on the held-out split) without added model complexity cost.

02

Route pages by archetype, not a single "refresh" bucket. Fix CTR, Refresh, and Support imply different editorial actions — but only Fix CTR currently shows a decline rate clearly above the base rate, so weight it accordingly.

03

Treat the top of the queue as the trustworthy core. Precision degrades past the top of the ranking; use the highest-ranked items with the most confidence and treat lower-ranked ones as directional.

04

Do not automate content edits, deletions, or client-facing forecasts from this system — it should only ever narrow a human's queue.

05

Set monitoring triggers: re-validate if a fresh sample's precision@50 drops more than one standard deviation below the historical grouped-split mean, if the base decline rate shifts more than 10 points, or at minimum quarterly.
